# 昂跑（On Running）线下门店排队系统 —— 设计文档（Design）

> 版本：v0.1（PoC 前设计稿）
> 状态：待评审 / 大方向已收敛
> 适用范围：线下门店"扫码取号"排队（virtual queue）服务

---

## 0. 文档目的

本文档记录排队系统在进入 PoC 编码之前的需求分析与架构决策，作为后续实现的依据。
内容分三部分：

1. **High Level 需求分析** —— 确定大方向（便利性、合规、国际化、服务独立性）。
2. **Detailed 功能分析** —— 确定关键机制（client 识别、状态保持、分批叫号、运营后台、异常处理等）。
3. **实现** —— 确定技术架构（独立 monorepo、NestJS + 轻前端）。

---

## 1. High Level 需求分析

### 1.1 核心设计原则

排队取号的现场体验必须**简单、丝滑**。体验设计的核心目标人群是**"中间摇摆派"客户**，而非两端的极端客户（铁杆会员 / 坚决不参与者）。

> 设计铁律：**任何一次"输入 / 授权 / 注册"动作，都是漏斗中的潜在流失点。** 取号主链路上的用户操作数应趋近于零（理想：扫码即得号）。

### 1.2 不限定微信小程序（国际化优先）

- 扫码终端**不限定**微信小程序，任何支持 H5 的浏览器/容器均可：微信、支付宝、WhatsApp 内置浏览器、Chrome、Safari 等。
- **理由**：本服务当前 for China，但需为未来 **global service** 复用预留空间。微信小程序存在平台审核、强绑定、海外不可用三重限制，不符合全球化目标。

### 1.3 不要求注册会员

- 取号**不要求**注册或登录会员。
- **理由**：排队属于"低承诺、即时性"服务。参考国际惯例（餐厅 waitlist、主题乐园 virtual queue），强制注册违背场景预期，是典型劝退点。

### 1.4 不要求输入手机号

- 取号**不要求**输入手机号，主链路也不做手机号采集。
- **理由（便利 + 合规双重）**：
  - 手机号属个人信息，一旦采集即触发 **PIPL（中国个人信息保护法）/ GDPR** 的告知-同意、加密存储、最小化、可删除、跨境传输等一整套义务。
  - 在取号页显式展示冗长 agreement 会严重破坏"丝滑"体验，对个人信息敏感用户更是高概率劝退。
  - **场景判断**：店内排队 = 用户人在店内或店附近、等待时间短、无需离店。"手机号短信通知"解决的是"离店远程等待"问题，而本场景该问题几乎不存在 → 手机号是"看似贴心、实则引入大合规成本又不解决真问题"的**伪需求**，一期砍掉。
  - 远程提醒若未来确有需要，再以 **opt-in 增值功能** 引入，且优先选择**不落地个人信息**的渠道（微信模板消息临时 openid、PWA Web Push），而非手机号。

### 1.5 独立服务（不与微信 / common 等 China service 耦合）

- 排队系统是一个**完全独立的服务**：独立 repo、独立部署、独立数据库，**不复用** China 侧的 gateway / common / customer 等微服务。
- **理由**：
  - 现有 gateway / common 绑定了 China 的鉴权、合规与基础设施假设；强行复用会把这些假设带入一个本应"全球中立"的服务，损害未来全球复用能力。
  - 排队服务的合规面（**匿名、零个人信息**）与会员系统差异巨大，物理隔离反而**降低整体合规风险**，避免合规义务外溢到会员体系。

> 关键澄清：实现"全球中立可复用"靠的是**架构边界**（不 import China 模块、不依赖 China 鉴权/基础设施），而非更换编程语言。

### 1.6 BI 数据割裂的 trade-off（可接受）

- 排队服务与会员系统**默认无数据联系**，这对 BI 看似不友好，但该 trade-off **合理且应接受**：
  - 架构上必须独立（合规与全球化要求）。
  - BI 并不会真的"断"：排队服务仍可产出**匿名行为数据**（取号量、平均等待时长、放弃率、时段峰谷、门店对比），运营价值高且不涉个人身份。
  - 预留**自愿绑定**口子（见 §2.6），当用户主动登录会员或在 POS 关联订单时，实现"匿名为默认、实名为可选"的渐进式数据贯通，给 BI 留升级路径。

### 1.7 隐私与合规底线

- 即便不收集个人信息，也提供**极简隐私说明**（一行字 + 可展开详情）。
  - 文案示例："我们仅用一个匿名标识为你保留排队号，不收集你的个人信息。"
- **指纹（Fingerprint）合规立场（正式条款）**：
  - UA + Canvas + 屏幕参数等浏览器指纹在 **iOS Safari / 隐私浏览模式下极不稳定**，且**采集指纹本身即属于采集个人信息的行为**（踩 PIPL / GDPR 合规线）。
  - 因此**指纹绝不作为身份主键**，仅可作为**辅助风控（防刷号）**手段。身份识别一律使用服务端签发的匿名 token（见 §2.1）。

### 1.8 国际化预留

- 一期即预留国际化抽象层，但**不提前实现**多通道（避免过度设计）：
  - 文案 i18n（中 / 英起步）。
  - 时区按门店配置。
  - 通知通道做成**可插拔接口**，一期只实现"页面内提示"一个实现。

## 2. Detailed 功能分析

### 2.1 Client 识别（无注册、无手机号）

采用**分层识别策略**，而非单一手段：

**主键识别：服务端签发匿名 token（推荐主方案）**

1. 用户首次扫码 → 服务端生成匿名 `clientId`（UUID）+ 创建排队记录。
2. 通过 **HttpOnly Cookie + 持久化 token** 下发给浏览器；同时落地页 URL 携带 token（见 §2.2）。
3. 同一设备重复扫码：浏览器自动带上 Cookie → 服务端识别为同一 client → 返回其已有号码（拒绝重复取号）。
4. 此为国际主流 virtual queue（主题乐园、餐厅 waitlist）的通用做法，全程零用户输入。

**辅助风控：门店码签名 + 轻量指纹**

- 门店二维码采用**静态码 + 服务端签名校验**（PoC 方案，详见 §2.9），而非依赖二维码本身动态刷新——门店多为贴纸 / 立牌，无屏幕设备，动态刷新不现实。
- 轻量指纹仅用于**防刷号风控**，不作身份主键（见 §1.7）。

### 2.9 门店码签名方案（PoC 确定）

- **形式：静态门店码（固定贴纸 / 立牌）**，内容为带签名的 URL：
  - `https://q.on.com/s/{storeId}?sig={signature}`
  - `signature = HMAC-SHA256(storeId, STORE_QR_SECRET)`，**长期有效**，仅用于验证"这是一个合法门店码"、防止伪造任意 `storeId` 刷号。
- **防刷的真正防线在取号接口，而非二维码本身**：
  - 同 client token **幂等**：已有有效号则返回原号，不新建（见 §2.1）。
  - 同设备 / IP + `storeId` 的**内存限流**（PoC：如 N 秒内最多取号一次）。
- **PoC 不引入**密钥轮换与签名有效期（避免过度设计）；这些留待生产阶段，配合后端密钥管理一并实现。

### 2.2 状态保持与页面回访

核心原则：**状态在服务端，页面只是视图。** 号码绑定在服务端，不绑定页面，因此页面关闭不丢号。

- **落地页即短链**：扫码后浏览器打开的 URL 本身就是可回访短链，形如 `q.on.com/t/{token}`，token 同时写入 HttpOnly Cookie。
- **三条回访路径**：
  1. 浏览器历史 / 收藏夹（靠 URL token）。
  2. 截图保存当前页（靠 URL token）。
  3. 重新扫同一门店码（靠 Cookie）。
- **"提供短链"的形式**（按成本从低到高，默认采用最低成本项）：
  1. （默认）页面顶部一行提示"截图保存此页即可随时回来" + 一个【保存 / 收藏】按钮，零成本、无需用户输入。
  2. iOS / Android 的 **Add to Home Screen**（PWA），生成临时图标。
  3. 临近叫号时**才**弹出 opt-in 提醒选项（见 §1.4，一期不做手机号）。

### 2.3 实时进度推送

- 使用 **SSE（Server-Sent Events）** 进行单向进度推送（比 WebSocket 更轻，契合"单向进度通知"场景）。
- 断线自动重连后，凭 token 拉取最新状态进行对账。

### 2.4 叫号机制：Ready Pool 缓冲区模型（分批 / 动态补位）

本场景**不同于餐厅座位**（餐厅是"一桌走才能下一桌"的强串行约束）。昂跑门店是**导购 / 试鞋 / 咨询**型服务，**并行服务能力 = 在岗店员数 N**，属多通道。

**结论：不采用纯逐个叫号，也不采用一次性大批量叫号，采用"Ready Pool 缓冲区"模型。**

- **模型定义**：系统始终维持"当前服务能力 + 缓冲"数量的用户处于"请到 X 区 / 轮到你了"激活状态。
- **容量自动计算（核心逻辑）**：
  - 公式：`容量 capacity = staffCount + buffer`。
  - `staffCount`：门店在岗店员数，**可在运营后台手动修改**（实时生效）。
  - `buffer`：固定缓冲位（PoC 取 `buffer = 1`），用于在某店员刚空出时让下一位用户提前就位、减少空窗。
  - 例：`staffCount = 3` → `capacity = 4`，即常态保持 4 个号处于 `READY`。
  - 店员手动调小 `staffCount` 时若当前 `READY` 数已超过新容量，**不强制踢出**已激活的号，仅暂停补位直到回落到容量以内（避免打断正在就位的用户）。
- **补位逻辑**：有人完成服务 / 取消 → `READY` 数低于 `capacity` → 自动从队列头部（`WAITING`）补一个号进入 Ready Pool → 该用户页面状态变为"轮到你了"。
  - 本质：**逐个补位、批量在场** —— 既不让用户傻等，也不让店员空转。
  - **批量叫号**：除逐个"下一位"外，运营后台提供**一键批量叫号**（如 Call next 10），高峰开场时快速放号。
- **可配置时间参数（门店级，存 SQLite，运营后台可改）**：
  - `readyTimeoutMinutes`：`READY` 多久未响应自动过号（转 `MISSED`）。
  - `recallWindowMinutes`：`MISSED` 的可召回窗口时长。
  - `servingAlertMinutes`：`SERVING` 超过该时长在后台高亮告警（仅提醒，**不自动**结单）。
  - 三者均有默认值，按门店独立存储，可在运营后台实时修改。
- **过号处理（降级 + 召回窗口，超时失效）**：
  - Ready Pool 中的号若超过 `readyTimeoutMinutes` 未响应，自动转 `MISSED`（进入独立"过号"区，并以转入时刻重置计时起点）。
  - `MISSED` 号在 `recallWindowMinutes` **召回窗口内**可被店员**一键召回**（回到 `READY`），体验更友好。
  - 召回窗口**超时后自动失效**（转 `CANCELLED`），从过号区移除，提示顾客重新取号 —— 避免 `MISSED` 无限堆积。此为相对早期"永不作废"设想的**显式策略升级**。

### 2.5 门店与队列模型

- **门店独立**：号码在门店内自增，门店之间互不影响。
- **不区分服务类型**：每门店一条**单队列**（模型不引入 queueType 维度，保持简化）。

### 2.6 会员归因绑定（Ticket ↔ memberId，预留 + UI mock）

实现"匿名为默认、实名为可选"的渐进式数据贯通，**面向 data science 的未来兼容**。一期落地范围：**预留 Ticket 级字段 + 用户端 UI mock + 本节文档**；不做真实绑定逻辑。

**绑定挂在 Ticket（不是 Client）—— 事件归因快照：**

- 绑定 = 给**单张票**写入一个 `memberId`（+ `memberBoundAt`）。这是一个**不可变的归因快照**："这张票在它生命周期内被归因给了谁、何时归因"。
- 为什么挂 Ticket 而非 Client：同一浏览器可能多次排队、店内共享设备、家人拼手机，"Client 当前 memberId"无法准确回答"当时那次排队算谁的"。Ticket 级快照避免可变维度被后续操作污染，是数仓归因的标准做法（类比订单快照价格而非引用商品现价）。

**`memberId` 是平台无关的不透明字符串（关键约束）：**

- queue 系统**不解析、不调用任何会员服务**，只存这个字符串。它可以是任意会员体系的 ID —— **不假设微信**。
- **单向引用**：queue 只引用 member，绝不反向写会员库；BI 侧通过该字段 join。queue 由此保持匿名 / 独立 / 可全球复用。
- **可选**：字段可空，无 membership 的市场完全不受影响。

**触发点（生命周期中何时引导关联）：**

- 仅在 **`SERVING`（店员开始服务）起、持续到 `DONE`（完成）** 显示"关联会员"入口 —— 此时购买意图最高、归因质量最好；`WAITING/READY` 太早（骚扰 + 噪声），`MISSED/CANCELLED` 无成交不显示。
- **来源与调用方取决于集成方**（通用 H5 下没有微信静默授权）：
  1. **顾客端**：点"登录关联会员" → 跳品牌会员登录页（OAuth / H5 登录）→ 回调带回 member id → 顾客浏览器调用绑定接口。
  2. **POS 端**：结账时 POS 后端按取号号 / 订单回填 member id。

**预留的 API（设计契约，PoC 未实现）：**

```
POST /api/tickets/:id/bind-member   body: { storeId, memberId }
```
写入该票的 `memberId` + `memberBoundAt`（一次性、不可变）。PoC 中用户端仅以本地 mock 模拟"跳转登录 → 关联成功"，不落库。

**业务诱饵（等价交换，仅在高意愿节点抛出，绝不放取号入口）：**

- 诱饵 1：绑定会员享**等待期专属优惠券 / 优先权益** —— 把"等待时间"变为可兑换价值。
- 诱饵 2：**等待时长累积会员积分** —— 把枯燥等待转化为忠诚度激励。
- 诱饵 3（成交后）：结账时"关联订单享会员售后 / 延保" —— 已成交、授权意愿最高，转化最佳。

### 2.7 运营后台（一期最小集）

供店员 / 店长使用：

- 实时队列看板（Waiting / Ready / Serving / Missed 四列，按业务流转方向排列）。
- 叫号 / 下一位（触发 Ready Pool 补位），含**一键批量叫号**（Call next 10）。
- 过号召回（召回 `missed` 号；超出召回窗口则不可召回）。
- **服务超时告警**：`SERVING` 超过 `servingAlertMinutes` 高亮提示，仅提醒、不自动结单（避免误关闭仍在服务的顾客）。
- 在岗店员数 `staffCount` 与时间参数（§2.4）实时编辑。
- 清场 / 重置队列。
- （后续）数据统计页：取号量、平均等待时长、放弃率、时段峰谷、门店对比。

### 2.8 异常处理（一期基本覆盖，不过度防御）

- **重复取号拦截**：同 token / 同设备返回原号，不新建。
- **刷号限流**：基于门店码签名 + 轻量指纹辅助风控做限流。
- **断线重连**：SSE 断线重连后凭 token 拉取最新状态对账。
- **闭店清队**：营业结束后清理 / 重置队列。
- **无效 / 过期 token**：优雅降级，提示用户重新扫码取号。

## 3. 实现

### 3.1 架构总览

- **独立 repo**：全新仓库，独立部署、独立数据库，**不复用** China 侧 gateway / common。
- **Monorepo 前后端一体**：前端 H5 与后端 API 同 repo、一体化部署、统一 CI/CD，便于小型独立服务维护。
- **技术栈：NestJS（后端）+ 轻量前端框架（前端）**。
  - 选择 NestJS 而非 Python/Flask 的理由：契合团队现有 NodeJS/NestJS 技能栈，复用现有 CI/CD / 监控 / 日志体系，避免异构维护负债；同时通过架构边界（不 import China 模块、不依赖 China 鉴权/基础设施）实现"全球中立可复用"。
  - 前端选轻量框架（React / Vue）而非服务端模板渲染：排队页是实时、状态驱动、需 SSE 推送的交互界面，天然适合"前端框架 + 后端 API"。

### 3.1.1 PoC 基础设施取舍（轻量优先）

- **数据库：SQLite**（而非 PostgreSQL/MySQL）。
  - 理由：零运维、单文件、随仓库即跑，足够支撑取号 / 状态 / 队列。
  - 通过 ORM（TypeORM / Prisma）抽象，生产切换 PostgreSQL 成本低。
- **不引入 Redis**。
  - Redis 在生产的价值（SSE 多实例广播、分布式锁、限流计数）在 **PoC 单实例**下均可用进程内实现：
    - SSE 推送：进程内 `EventEmitter` / RxJS。
    - 补位串行：单进程串行处理，天然无锁。
    - 限流：内存计数器。
  - **设计约束**：将这些能力封装为接口（如 `EventBus`、`RateLimiter`），PoC 提供内存实现，生产替换为 Redis 实现，避免日后重写业务逻辑。


### 3.3 领域模型（草案）

**Store（门店）**
- `id`、`name`、`timezone`、`staffCount`（在岗店员数，决定 Ready Pool 容量）。
- 时间参数（门店级，运营后台可改）：`readyTimeoutMinutes`、`recallWindowMinutes`、`servingAlertMinutes`（见 §2.4）。
- **门店码签名密钥**：PoC 采用**全局**环境变量 `STORE_QR_SECRET`（所有门店共用），per-store 密钥（`qrSecret` 字段）留待生产阶段。

**Client（匿名客户端）**
- `id`（UUID，匿名主键）、`createdAt`、`memberId`（可空，历史预留；归因实际挂在 Ticket，见下）。

**Ticket（排队号）**
- `id`、`storeId`、`clientId`、`number`（门店内自增）、`status`、`createdAt`、`calledAt`、`servedAt`。
- **会员归因（预留，PoC 未实现）**：`memberId`（可空，平台无关的不透明会员标识）、`memberBoundAt`（绑定时刻）。作为**不可变归因快照**挂在票上，供 data science 把匿名排队事件归因到会员（见 §2.6）。
- `status` 取值见 §3.4。

### 3.4 排队状态机

```
WAITING ──(进入 Ready Pool)──► READY ──(店员确认服务)──► SERVING ──► DONE
   │                              │
   │                              └──(超时未响应)──► MISSED ──(店员召回)──► READY
   │                                                  │
   │                                                  └──(召回窗口超时)──► CANCELLED
   └──(用户放弃 / 闭店清队)──► CANCELLED
```

- `WAITING`：排队中。
- `READY`：已进入 Ready Pool，页面提示"轮到你了 / 请到 X 区"。
- `SERVING`：店员已确认开始服务。
- `DONE`：服务完成（触发自动补位）。
- `MISSED`：过号（在召回窗口内可被召回）。
- `CANCELLED`：用户放弃、闭店清队，或**过号召回窗口超时自动失效**。

### 3.5 API 草案（REST + SSE）

**用户侧**
- `POST /api/tickets` —— 扫码取号（带门店码签名）；若同 client 已有有效号则返回原号（幂等）。
- `GET  /api/tickets/me` —— 凭 token / Cookie 获取当前排队状态（回访 / 重连用）。
- `GET  /api/tickets/me/stream` —— SSE 实时进度推送。
- `DELETE /api/tickets/me` —— 放弃排队。
- `POST /api/tickets/:id/bind-member` —— 会员归因绑定（**预留契约，PoC 未实现**；body `{ storeId, memberId }`，见 §2.6）。

**运营后台侧**
- `GET   /api/admin/stores/:storeId/queue` —— 实时队列看板（含 Waiting/Ready/Serving/Missed）。
- `POST  /api/admin/stores/:storeId/call-next` —— 下一位（触发 Ready Pool 补位）。
- `POST  /api/admin/stores/:storeId/call-next-batch` —— 批量叫号（body: `count`）。
- `POST  /api/admin/stores/:storeId/staff-count` —— 修改在岗店员数（body: `staffCount`）。
- `POST  /api/admin/stores/:storeId/rules` —— 修改门店时间参数（`readyTimeoutMinutes` / `recallWindowMinutes` / `servingAlertMinutes`）。
- `POST  /api/admin/tickets/:ticketId/serve` —— 确认开始服务。
- `POST  /api/admin/tickets/:ticketId/done` —— 完成服务（触发补位）。
- `POST  /api/admin/tickets/:ticketId/miss` —— 手动标记过号。
- `POST  /api/admin/tickets/:ticketId/recall` —— 召回 `missed` 号（受召回窗口限制）。
- `POST  /api/admin/stores/:storeId/reset` —— 清场 / 重置。

> 鉴权说明：用户侧基于匿名 token（HttpOnly Cookie）。**PoC 阶段运营后台 API 不做鉴权**（仅本地 / 演示用），店员 / 店长登录鉴权留待二期（本服务自有账号体系，不依赖 China gateway）。

### 3.6 一期范围（PoC）与二期预留

**一期（PoC）实现：**
- 匿名 token 识别 + 取号幂等 + 状态查询。
- SSE 实时进度。
- Ready Pool 分批叫号（容量自动计算，店员数可手改）+ 一键批量叫号。
- 过号机制：READY 超时自动过号 + 召回窗口内一键召回 + 窗口超时自动失效。
- 服务超时告警（仅提醒，不自动结单）。
- 门店级可配置时间参数（readyTimeout / recallWindow / servingAlert），存 SQLite、运营后台可改。
- 运营后台最小集（**不鉴权**）。
- 基本异常处理（§2.8）。
- 极简隐私说明、i18n 抽象层（中/英）。
- 基础设施：**SQLite + 进程内实现（无 Redis）**。

**二期预留（仅留接口 / 数据结构，不实现）：**
- 运营后台店员 / 店长登录鉴权。
- 匿名 clientId ↔ 会员 ID 自愿绑定（§2.6）及业务诱饵。
- opt-in 远程提醒（PWA Web Push / 微信模板消息等不落地个人信息的渠道）。
- BI 数据统计页扩展。
- 生产基础设施替换：PostgreSQL + Redis（EventBus / RateLimiter 接口的 Redis 实现）。

## 4. 待办 / 开放问题

- 门店码签名的密钥轮换与签名有效期方案，留待生产阶段（PoC 采用全局长期有效签名，见 §2.9 / §3.3）。
- 运营后台店员鉴权的具体实现（本服务自有账号体系），留二期（见 §3.5 / §3.6）。
- `buffer` 缓冲位取值是否随高峰时段调整，待运营数据验证（PoC 固定 `buffer = 1`，见 §2.4）。
- 过号召回的排位策略：当前召回直接回到 `READY`（可能短暂超出容量）。生产可考虑"待召回队列"模式（Ready 满时优先于 Waiting 补位）以兼顾公平，待运营验证。
- 设备识别跨 App 浏览器隔离：同一手机不同内置浏览器（微信/支付宝/Chrome）会被识别为不同 client。PoC 可接受；正式版若需"一人一号"需依赖手机号/会员/平台 openid 等主动标识（见 §2.6）。
